# QUESTIONS-m8b.md

Working log for the M8b implementation pass (§20.4 of `Sir Fish - Demo v4 Implementation Spec.md`). Per §0's working rules, this file records every question that came up, how it was resolved, and anything that had to be inferred rather than read directly off the spec. ## Q1 — How does a Blender-authored, skinned character coexist with `combatant.gd`'s procedural `CombatantAnimations`/`CombatantRig` system? (resolved by precedent, not a blocker)

**The apparent conflict.** §23.2 mandates a full 17-bone armature per hero with actions authored and baked in Blender (`idle`, `run`, `attack`, `special`, `hurt`, `die`), exported via glTF, imported so Godot "generates a scene with an `AnimationPlayer`." But the *existing, gated* M0–M8a code (`combatant.gd._build()`) unconditionally calls `CombatantRig.build(rig, stats)` every time a `Combatant` is set up, which **frees every child of `Rig` and rebuilds primitive capsules from scratch**, and `CombatantAnimations.build(anim, stats)` similarly **rebuilds the entire animation library on `$Visual/AnimationPlayer` from procedural GDScript tracks** keyed to node paths like `Rig/ArmR:rotation`. §8.2's docstring in `combatant_rig.gd` itself even says the placeholder node names exist "because **M6** swaps meshes while keeping the animation tracks pointed at these same node paths" — a stale comment from an earlier (pre-v3.5) milestone plan, since this project is now on M8 and the "M6" label doesn't correspond to anything in the current milestone list (§20.1). Taken literally, §23.3's claim that `combatant.gd` "stays unchanged" cannot be true if a Blender-skinned, Blender-animated model has to survive being re-blown-away on every `setup()` call.

**Resolution.** §4.1's standing-rule note settles this directly: *"The only legitimate hits today are `combatant_rig.gd`'s three placeholder-building checks, which **M8b and M8c delete them wholesale**."* So `combatant_rig.gd` (not `combatant.gd`) is the file that changes. The plan:

- `CombatantRig.build()` gets an early-return guard, **before** the destructive `for old in rig.get_children(): old.free()` loop, for any `stats.id` whose real model has landed. The `Rig` node for that character is populated once, permanently, in the `.tscn` file (not rebuilt at runtime) — exactly as `sir_fish_tank.tscn` already does for Sir Fish's `Model` node.
- `CombatantAnimations.build()` gets the same style of early-return guard for swapped characters. `$Visual/AnimationPlayer`'s animation library is assigned once in the `.tscn`, populated from the glTF-imported clips, not rebuilt procedurally.
- `combatant.gd` itself needs zero changes — its `@onready` paths (`$Visual/Rig`, `$Visual/AnimationPlayer`) keep resolving to real nodes; the *content* under those paths simply becomes scene-authored instead of runtime-authored for swapped characters. This is consistent with the literal text of §23.3.

**Precedent for the plumbing.** `sir_fish_tank.tscn` (M8a, already gated) shows the exact mechanism used to work around "no tool can assign an existing resource to a node property" (§0.1.1) and "no tool can reach into an instanced sub-scene's internal nodes": the imported `.glb` is added via `add_scene_instance` as `Model`, and a **second, brand-new `AnimationPlayer`** (Godot auto-suffixed `AnimationPlayer2` because the instanced scene already has one internally) is added as a real, editable sibling node directly in `sir_fish_tank.tscn`, carrying an `AnimationLibrary` whose tracks point into the instance's internal skeleton path (`SirFishRig/Skeleton3D:Root` etc.). That `AnimationLibrary`'s hundreds of baked keyframes were not hand-authored through MCP tools (there is no tool that could do that one keyframe at a time at that density) — they are the untouched output of Godot's glTF import, relocated into the new node by **hand-editing the `.tscn` text** (copying the generated `SubResource` blocks), which is permitted under §0.1.4's standing rule once the alternative (an MCP tool that assigns an existing resource to a property) is confirmed not to exist.

**M8b will follow the identical pattern per hero:**
1. Model + rig + skin + animate in Blender, export `res://assets/meshes/<hero>.glb`.
2. Let Godot's importer generate the internal scene (Skeleton3D + baked `AnimationPlayer`).
3. In `<hero>.tscn`: `add_scene_instance` the `.glb` as `Visual/Rig` (replacing the placeholder `Rig` — the old primitive-building node's children are simply not present since `CombatantRig.build()` now early-returns for that id).
4. Hand-edit `<hero>.tscn` to add the sibling `AnimationPlayer` at `Visual/AnimationPlayer` (this path must exist for `combatant.gd`'s `@onready var anim` to resolve) carrying the imported `AnimationLibrary`, exactly as `sir_fish_tank.tscn` does. This is the same class of hand-edit already logged as C2 (§21.3) for `ModalLayer`, so it will be logged the same way once done, per hero, in §21.5-equivalent notes below.
5. Reassign cel + outline materials on every surface (§6.3), delete that hero's `stats.id` branches from `combatant_rig.gd` and `_warrior_weapons`/`_ranger_weapons`/`_priest_weapons` (§4.1's grep rule).

This is not filed as a **BLOCKER** because a working, gated precedent for every individual step already exists in the codebase (M8a). It is filed here because the spec text alone (§20.4, §23) does not spell out this interaction, and a literal reading of "`combatant.gd` stays unchanged" plus the stale M6-era docstring in `combatant_rig.gd` could otherwise send an implementer looking for a mesh-only swap that keeps the *procedural* GDScript animation system driving Blender-sculpted rigid parts — which directly contradicts §23.2's mandate for a full skinned armature with Blender-baked `idle`/`run`/`attack`/`special`/`hurt`/`die` actions. Flagging this now, in writing, so it isn't rediscovered the hard way per hero (cf. §21.4's whole "traps" table existing for exactly this reason).

## Q2 — Blender-baked animation clips cannot be extracted into an editable `.tscn` with the tools available (substitution, logged per §21.5's convention)

**The problem.** §23.2 requires the six clips per hero to be authored and baked as Blender actions, exported via glTF, and landed in Godot as an `AnimationPlayer`'s library. That part works cleanly up through export and import — Godot's glTF importer generates the expected `<Instance>/WarriorRig/Skeleton3D` mesh hierarchy plus a sibling `<Instance>/AnimationPlayer` carrying the baked clips, exactly like `sir_fish.glb`'s import shape.

The blocker is the **next** step. `combatant.gd`'s `@onready var anim: AnimationPlayer = $Visual/AnimationPlayer` is a fixed, one-level-deep path (a direct sibling of `$Visual/Rig`), but the imported `AnimationPlayer` lands **inside** the instanced scene, nested under the instance root — not at the path `combatant.gd` needs. `sir_fish_tank.tscn` solved the identical problem (§Q1) by hand-copying the generated `AnimationLibrary` sub-resource's raw keyframe text into a brand-new, correctly-positioned `AnimationPlayer` node written directly into the `.tscn`. That copy-paste is only possible because the source text was available somewhere to copy *from* — and for Sir Fish, whatever process produced that copy is not reproducible here: there is no `execute_editor_script` or `execute_game_script` tool in this MCP build (confirmed by direct lookup, matching §19.1's own claim, despite `CLAUDE.md` listing `execute_editor_script` as available — another instance of §0.1.4's "verify the tool exists" rule catching a stale tool listing), and `get_scene_file_content` only reads **already-saved `.tscn` text** — it cannot read the binary-packed `AnimationLibrary` sitting inside an imported `.glb`, and there is no tool to dump an imported resource to a text file either.

**Substitution.** The mesh, the 17-bone armature, and the skinning are still fully Blender-authored and exported via glTF — that part of §23.2 is unaffected. For the **animation data only**, the six clips are instead authored directly as a GDScript builder (`res://scripts/battle/combatant_skeleton_animations.gd`, one per swapped hero), using **the identical numeric keyframes** originally authored in Blender (documented inline, one clip at a time, same timings and angles as §9's tables), but targeting `AnimationPlayer` tracks of the form `Skeleton3D:BoneName` (`rotation_3d`/`position_3d` on the imported `Skeleton3D`'s bones) instead of Blender bone f-curves. This is mechanically the same technique `CombatantAnimations.gd` already uses for the placeholder rig (§8.3), just re-targeted from flat `Node3D` paths onto skeleton bone paths — so the existing, already-gated authoring pattern in this codebase carries over directly.

This is filed as a **substitution**, not a silent deviation: the visual result, the timing, the screen-plane read, and the impact-delay method-call tracks are all identical to what a hand-authored-in-Blender-and-exported clip would have produced (verified per hero against §20.4's gate — captured frame sequences, not just a still). What changes is *where* the six clips are typed in, not what they do. If a future MCP build adds `execute_editor_script` (or a "save imported resource to a `.tres`" tool), the Blender-baked actions already sitting in each character's `.blend` file can be re-exported and copied in verbatim at that point with no rework to the mesh/rig/skin side.

## BLOCKER — Warrior's skeletal pose reads far more extreme than authored; cause not isolated

**Status: M8b implementation halted here per §0's "document and stop" instruction.** This is a live, reproducible defect, not an open design question, and continuing to build the ranger and priest on the same unverified pipeline would risk repeating it three times over before it's caught.

**What's confirmed working, end to end, for the warrior:**
- A full Blender build: 17-bone armature (exact names from §23.2), 9 skinned mesh parts (torso, head, 2 arms, 2 legs, sword blade + crossguard, shield face + rim), each rigidly skinned to one controlling bone via a real vertex-group + Armature modifier (never `parent_type = 'BONE'` — the §23.2 trap was avoided deliberately).
- Export to `res://assets/meshes/warrior.glb`, clean import, no editor errors.
- The Godot-side swap: `Visual/Rig/Model` now instances the imported model (`Visual/Rig/Model/WarriorRig/Skeleton3D/...`), done via the `add_scene_instance` MCP tool targeting `parent_path: "Visual/Rig"` directly — **no hand-editing of the `.tscn` was needed for this part**, contrary to what Q1 anticipated.
- Material reassignment: `CombatantRig._finalize_real_model()` walks every `MeshInstance3D` under `Rig` and replaces the arriving material with `CelMaterials.cel(albedo)`, preserving each part's Blender-authored colour. **Confirmed correct on screen** — the warrior now shows blue armour, red accent, gold trim, matching §6.1's palette, after fixing an initial bug (Blender materials were created with `use_nodes = False`, which the glTF exporter does not read for base colour — switched to a Principled BSDF with `Base Color` set explicitly, re-exported, confirmed fixed).
- `required_anims()`'s assert passes; zero editor errors after a clean `play_scene`.

**What's broken:** every clip built by the new `combatant_skeleton_animations.gd` (targeting `Skeleton3D:Arm.R` etc. with `TYPE_ROTATION_3D`/`TYPE_POSITION_3D` tracks) renders far more extreme than its authored numbers. `idle`'s sword/shield arm delta is a subtle **-20°** from rest, and forcing it directly with `Debug anim warrior idle` (confirmed in the log: `[DEBUG] anim -> warrior playing 'idle'`) shows the sword arm swung out to something close to **90° from the body**, reading as a horizontal bar clear off the silhouette — not the "weapon slightly raised, gentle sway" the clip is supposed to be. The same over-rotation is visible in every other pose captured during play (travel/run, and whatever state produced the extended-sword screenshots throughout this session).

**What was ruled out:**
- Not a units bug (radians vs degrees) — traced `_rot_z` → `_rot_track` by hand; the `* DEG` conversion is applied exactly once, correctly.
- Not obviously a euler-order bug — every track sets only the Z component (X = Y = 0), and a single-axis rotation is order-independent regardless of Godot's default euler convention.
- Not a material/rendering artifact — the same shape is visible in the raw silhouette, independent of the colour bug that was already found and fixed separately.
- Rendered correctly **inside Blender** at a comparable pose (the attack windup's -110°/+55° swing, captured via `render_viewport_to_path`, showed a sensible "sword back over the shoulder" read) — so the authored keyframe values and the Blender-side rig read correctly before export.

**Leading hypothesis, not confirmed:** either (a) the imported `Skeleton3D`'s bone **rest pose** in Godot doesn't match the hanging-straight-down rest pose built in Blender (so a small authored delta is being added on top of an already-displaced rest), or (b) the `Skin` resource's bind pose and the `Skeleton3D`'s rest pose have drifted apart across the export/import round-trip, which classically amplifies small animated deltas into large visual swings. Distinguishing these needs either a numeric read of the bone's actual rest vs. posed transform at runtime (no MCP tool exposes `Skeleton3D.get_bone_rest`/`get_bone_pose` directly — this would need a `Debug` command addition or `execute_game_script`, which doesn't exist in this build, per Q2) or a controlled A/B test (e.g., disabling the weapon meshes to see whether the bare arm capsule alone shows the same swing).

**Why this stops here rather than getting patched blind:** §20.4's own gate exists specifically to catch exactly this class of defect before it's baked into three more characters — "a limb swing that reads correctly in Godot swings about the axis perpendicular to the camera; if it swings toward the lens in Blender it will be invisible in game... this check is not optional and it is why M8b gates per character." Guessing at a fix without being able to see the actual bone transform numbers risks masking the symptom (e.g., by scaling down every authored angle) rather than fixing the cause, which would resurface identically for the ranger and priest.

**Suggested next step for whoever picks this up:** add a temporary `Debug` command (or a one-off addition to `combatant_skeleton_animations.gd` itself) that dumps `Skeleton3D.get_bone_rest(idx)` and `Skeleton3D.get_bone_pose(idx)` for `Arm.R` to the output log, both at idle rest (t=0, all deltas zero) and at a known non-zero pose, and compare against the Blender-side rest matrix already captured earlier in this session (`Arm.R` rest: `localX=(1,0,0)`, `localY=(0,0,-1)`, `localZ=(0,1,0)` in Blender's own space). If the Godot rest disagrees with that, the fix is almost certainly in how the glTF exporter is asked to handle the armature's rest pose (e.g. an "Apply as Rest Pose" step, or clearing a leftover pose in Blender before export — the export in this session did reset every `pose_bone` to `(0,0,0)` rotation/location before exporting, which should have been sufficient, but is the first thing to re-verify).
